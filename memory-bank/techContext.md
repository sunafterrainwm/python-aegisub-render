# 技術脈絡

## 工具鏈

- CPython 3.14（`C:\Program Files\Python314`）＋ uv；build backend `uv_build`（src layout，`module-root = "src"`），預設 group 是 `dev`
  （basedpyright、pytest、ruff、distlib，以及 cython、meson、ninja）；`build` group 也有 cython、meson、ninja。
- 執行期依賴：`regex`、`tqdm`；`av`（PyAV）是 `video` extra（只有真的要探測影片才需要，`video/probe.py`
  延遲 import，缺了會以「could not open video」的警告帶過）。dev group 裡寫了 `aegisub-render[video]`（自我引用 extra，版本只定義一次），
  所以這個 repo 自己的 `uv sync` 照樣會裝它；引用方要影片功能得寫 `aegisub-render[video]`。
- 原生建置：Visual Studio 2022 C++ x64、meson（根目錄 `meson.build`，subproject 在 `native/subprojects/`）、動態 CRT。

## 被別的專案引用

- **引用方可能同時依賴 CLI，不只 Python API。** 已知有呼叫端跑 `scripts/build_exe.py` 產的 exe：
  `aegisub-render render <ass> --font-dir <dir> --no-progress --keep-brand`，**就地覆寫**那個 `.ass`。
  所以這些算契約，重構內部可以、要改掉得先確認沒有呼叫端在用：`render` 子命令名、`--font-dir`／
  `--no-progress`／`--keep-brand` 的名稱與語意、「沒有 `-o` 就覆寫輸入檔」這個行為。`--keep-brand`
  對這種用法特別重要（輸出的檔頭要留住輸入本來的 `; Script generated by Aegisub …`，不可改寫成
  aegisub-render 的版本）。驗收重構時除了 `tests/test_cases.py` 的逐位元組比對，也要跑
  `tests/test_cli.py`、`tests/test_exe.py`。
- 只支援連結式安裝：`uv add --editable <repo>`。對方的 `pyproject.toml` 會寫成
  `[tool.uv.sources] aegisub-render = { path = "...", editable = true }`，環境裡放的是
  `site-packages/aegisub_render.pth`（內容就是 `<repo>/src` 這一行），沒有複製任何程式碼。
- 型別檢查：**命令列的 pyright / basedpyright 認得這種安裝**（它會讀 site-packages 裡的 `.pth`，而
  `uv_build` 寫的是「一行純目錄路徑」，不是 setuptools editable 那種 `__editable___*_finder.py`
  import hook；實測 basedpyright 1.40.2 在只有 `.pth` 的乾淨 venv 裡能完整解析
  `aegisub_render.macro.measure` 的型別）。**但 VS Code 的擴充功能實務上吃不到**，所以引用方還是要
  自己把這個 repo 的 `src` 加進對方 VS Code workspace 根目錄的搜尋路徑，二選一：
  `.vscode/settings.json` 的 `python.analysis.extraPaths`，或 `pyrightconfig.json` 的 `extraPaths`
  （後者連命令列的 pyright 都讀得到，但它存在時 Pylance 會完全忽略 `python.analysis.*`，所以不要
  兩個都放）。寫在 `pyproject.toml` 的 `[tool.pyright]` **不行** —— 實測 basedpyright 不讀那一節。
- 為了 mypy 與 PEP 561，`src/aegisub_render/py.typed` 必須存在（空檔）。
- 不要發佈 wheel：`.pyd` 是針對單一直譯器編好後 commit 進 repo 的，wheel 的平台／ABI 標記會是錯的。

## CI（GitHub Actions，`.github/workflows/ci.yml`）

push 到 `master`、每個 PR 與手動都會跑三個 job：`ruff`（check ＋ format）、`basedpyright`
（吃 commit 進去的 `.pyi`，不需要先建置）、`build and test`（windows-latest 與 ubuntu-latest
各一：裝相依、`native/build.py` 編兩個分支的原生模組、import 進來、再跑測試）。

**CI 刻意跑不完整個測試套件**：逐位元組的案例測試要有 Aegisub 3.5.1 的 automation 腳本，量字測試
要有錄製 fixture 時的那幾個 Windows 字型，hosted runner 兩者都沒有。所以 CI 只跑
`tests/test_{ass,crt,diff,output,stubs,sync_upstream}.py`（`PYTEST_TARGETS`），Windows 上多跑
`test_text_extents.py` 與 `test_exe.py`。**完整的 `uv run pytest` 仍然只在本機跑得完**，
改動渲染行為時不要只看 CI 綠燈。

Linux 的 job 會 `apt-get install libfontconfig-dev libharfbuzz-dev`；Windows 的 MSVC 環境由
`native/build.py` 自己用 vswhere ＋ `vcvars64.bat` 找，不需要額外的 action。

**Windows 上建置還需要 `sed` 在 PATH 上** —— LuaJIT 的 meson 會呼叫它。從 Git Bash 跑就有；
從 PowerShell 跑要自己把 `C:\Program Files\Git\usr\bin` 加進 PATH（CI 有一個步驟做這件事），
不然 meson setup 會停在 `Program 'sed' not found`。

相依更新由 Renovate 顧（`renovate.json`，用 `sunafterrainwm/renovate-config` 的共用設定），
workflow 裡 action 的版本也在它的管轄範圍。

## 常用指令

```powershell
uv sync                                            # repo 搬家後若 uv run 報 "trampoline failed"，用 uv sync --reinstall
uv run pytest                                      # pytest 設定含 -p no:faulthandler（LuaJIT 用 SEH 拋錯）
uv run basedpyright                                # strict，要 0 errors
uv run ruff check ; uv run ruff format --check
uv run python native/sync_upstream.py SOURCE [--ref REF] [--dry-run]   # 換 Lua 執行環境的來源（見 README）
uv run --group build python native/build.py        # 重編 .pyd 並重新產生 .pyi（tests/test_stubs.py 檢查一致）
uv run --group build python native/build.py --msys2 C:\msys64\ucrt64   # Windows 上編 Linux 分支（會取代 commit 的 .pyd；
                                                   # 之後跑一次一般建置換回）
                                                   # repo 搬家後先刪 native/builddir
AEGISUB_RENDER_UPDATE_SNAPSHOTS=1 uv run pytest tests/test_cases.py   # 重新記錄 snapshot（只在 Windows）
uv run python scripts/gen_cases.py                 # 以固定 seed 重新產生測試案例（CRLF）
uv run python scripts/build_exe.py                 # 產生 aegisub-render.exe
```

## WSL／Linux

```bash
# ~/.local/bin/uv（uv 自己管理的 Python 3.14）；venv 用 .venv-linux 和 Windows 的 .venv 分開
export PATH=$HOME/.local/bin:$PATH UV_PROJECT_ENVIRONMENT=.venv-linux UV_LINK_MODE=copy
cd /mnt/<drive>/<path-to-repo>
uv sync --group build && uv run --group build python native/build.py && uv run pytest
```

需要 fontconfig 與 HarfBuzz 的開發套件（Debian／Ubuntu：`libfontconfig-dev libharfbuzz-dev`）。
從 Windows 端呼叫：`wsl.exe -e bash -lc '...'`。

## 測試

- `tests/cases/` 12 個案例（CRLF，`.ass` 在 git 裡是 `-text`）；`tests/aegisub/` 是 Aegisub 用 `Karaoke template`
  濾鏡匯出的結果，`--filter` 的輸出必須逐位元組相同（只差 header 行），巨集輸出去掉 Project Garbage 後也相同；
  `tests/snapshots/` 是巨集的完整輸出。
- 缺少 Aegisub 參考檔的案例直接失敗；新增或重產案例後要在 Aegisub 匯出。

## 開發慣例（使用者的偏好）

- 回覆與文件用繁體中文（zh-TW）；程式碼、註解、commit message 用英文。
- 大的設計先用 grilling（逐輪提問）對齊再動手；忠於上游、偏離要說明。
- git：commit 有 GPG 簽章（`commit.gpgsign=true`，可能跳 pinentry，放背景執行並用
  `git log --show-signature -1` 確認），**不可**繞過簽章。
- **只 stage 明確的路徑，不要 `git add -A`**：使用者會在 repo 根目錄放自己的檔案（zip 等），
  也會在工作樹留下未提交的工作；碰到與自己無關的變更就不要動、不要一起 commit。
- 檔案編修避免 heredoc 裡的反斜線（Git Bash 會吃掉），改用編輯工具或寫成檔案的腳本。
